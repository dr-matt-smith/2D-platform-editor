# Version 6 — Implementation Plan

Status: Planned (design Draft; mapping resolved) · Date: 2026-05-18 ·
Design: [../1_design/version06_design.md](../1_design/version06_design.md)

A forward plan: v6 is not yet built. One milestone per commit, prefixed
`v6 …`, **path-scoped `git add`** (never `-A`) with a `git status` glance
before committing, `npm test` green and `npm run build` clean before each.

## Constraints & approach

- **No app code changes.** The loader is manifest-driven; the only logic
  touched is the build-time generator. `level.js`/`validate.js`/`levels.js`/
  `loaderDialog.js`/`main.js` are untouched.
- **No id churn / no migration** (design §3, confirmed). `below_ground` and
  `above_ground` files are not renamed or relabelled.
- `# order:` is an additive header directive. The `level.js` parser already
  *consumes any* `# key: value` header line (known keys handled, unknown ones
  skipped via the same `continue`) — so adding `# order:` to the level files
  needs no parser change and cannot affect validation. Verify this explicitly
  in M1 (parse+validate the edited files, 0 errors).
- New `tutorial.txt` is validated with the project's own `parse`+`validate`,
  exactly as the other example levels were.

## Milestone 2 — generator honours `# order:`

1. `scripts/gen-levels-manifest.mjs`: read an optional `# order:` directive
   (same directive regex it already uses for `# name:`); sort entries by
   `(order ?? 999, file)` instead of filename only. Manifest entry shape
   `{ id, name, file }` is **unchanged** (order influences array position
   only — the app consumes array order).
2. Regenerate via `npm run gen:levels` (the `predev`/`prebuild` hook also
   does this); commit the regenerated `manifest.json` (3 entries, order
   tutorial → below_ground → above_ground).
3. Dev smoke: `/data/levels/manifest.json` has 3 entries in that order;
   `/data/levels/tutorial.txt` serves `200`; app boots with `tutorial` as
   the default (fresh profile / no `lastOpen`).

Commit: `v6 m2: gen-levels-manifest honours # order: + regenerate`.

## Risks & sequencing

- **Generator sort stability.** `(order, file)` must be a total order;
  levels without `# order:` fall back to `999` then filename so the result
  stays deterministic. Assert the regenerated manifest is exactly the 3
  expected entries in the expected order before committing.
- **Manifest formatting.** Keep the existing `JSON.stringify(…, 2)` +
  trailing newline so the diff is just the entries, not reformatting.
- **`serialize()` omits `# order:`** (it only emits name/theme/size). This is
  *not* exercised by the app's load/save path — the loader loads raw text
  into the buffer and drafts/downloads preserve it verbatim; `serialize()` is
  only used by `level.test.js` round-trip. So bundled files keep their
  `# order:`. Flagged as a known, harmless asymmetry; no action in v6.
- **No tests change.** `levels.test.js` injects its own manifest, unaffected.
  Suite stays 52; build stays clean. Verification for v6 is parser-validation
  of the files + manifest assertion + dev smoke (no automated DOM test, the
  same standing gap since v2).

## Deferred / non-goals (design §11)

Per-tile variant randomisation; flood/line tool; reachability lint;
play-test runtime; level create/rename/delete (the feature that would make
id-rename + migration worth building). Not in v6.
