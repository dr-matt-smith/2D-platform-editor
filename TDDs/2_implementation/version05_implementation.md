## Constraints & approach

- **Tile selection stays a plain integer** (the v5 design decision). `pickTile`
  is pure and returns a number; `autotileIndex` is kept and delegated to for
  the non-thin path, so the existing v4 autotile tests are the regression
  guard that thick/boundary walls are byte-for-byte unchanged.
- Off-grid is solid (v4 §3) and that is reused as-is — it is exactly what
  makes edge-flush 1-wide columns *not* count as thin.
- The four new tiles are **committed artifacts** generated by an offline
  Python/PIL script (same toolchain that produced the original 24). It is
  *not* wired into `predev`/`prebuild`: tiles are static and Python may be
  absent in CI/other envs, unlike the levels manifest which must stay fresh.
- `tiles.json` is **extended** with entries 24–27; the original 24 are not
  re-sliced (avoids churn/risk to known-good assets).

## Milestone 1 — `pickTile` selector + tests

1. `renderer.js`: `export function pickTile(grid, r, c)` — first match wins:
   - all four neighbours open → `27` (isolated 1×1)
   - `left` & `right` open → vertical: up open `4` / down open `20` /
     else `12`
   - `up` & `down` open → horizontal: left open `24` / right open `26` /
     else `25`
   - else → `autotileIndex(grid, r, c)` (unchanged v4 9-slice)
   Reuse the existing `solid()` (off-grid = solid).
2. Extend `renderer.test.js`: 1-wide pillar (top/mid/bottom → 4/12/20),
   1-tall ledge (24/25/26), isolated cell → 27, edge-flush 1-wide column is
   *not* thin (stays a boundary 9-slice tile), thick block unchanged. The
   pre-existing `autotileIndex` tests must still pass untouched.

Commit: `v5 m1: pickTile thin-run/isolated selector + tests`.

## Milestone 2 — generate the four tiles

1. `scripts/gen-platform-tiles.py`: from `tiles/20,12,04`,
   `Image.rotate(-90, expand=True)` → `24_platform_left`,
   `25_platform_mid_h`, `26_platform_right`; compose
   `27_platform_single` = left 16 px of 24 + right 16 px of 26, then patch
   the seam column (sample/blend) so the join is clean. Append the four
   `tiles.json` entries (index, row/col `null` for derived, name, role
   `terrain`, file); leave entries 0–23 intact.
2. Run it; **visually verify**: caps face the correct ends (rotation sign),
   `mid_h` symmetric, and the `platform_single` seam is clean. If the seam
   is poor, fall back to a wider blend or a four-corner-quadrant composite
   (design §7) — selection logic is unaffected.
3. `tileset.js`: load the four standalone PNGs alongside the atlas (resolve
   when all settle; keep the graceful `ready:false` degrade);
   `drawTile(ctx,index,…)` sources index ≥ 24 from those images, < 24 from
   the atlas as today. No rotation code.

## Risks & sequencing

- **M1 is pure and first** — its safety net is the unchanged v4 autotile
  tests; if any of them move, the delegation is wrong.
- **Seam quality (M2) is the one unknown** — cannot be judged until rendered;
  the plan commits to visual verification with a named fallback rather than
  assuming. Generation is offline/deterministic, so iterating is cheap.
- **`tiles.json` extension** must be additive — a careless full regenerate
  could reorder/rewrite the committed 0–23. Append only; assert length 28 and
  entries 0–23 unchanged after running the script.
- **Example levels may not exercise the new tiles.** That is fine for
  regression (they should look identical), but the *new* behaviour is proven
  by `pickTile` unit tests + the scratch render, not by the example levels.
- **No automated canvas test** for image sourcing/seam — dev-smoke +
  render-harness only, the same honest gap carried since v2.

## Deferred / non-goals (design §9)

Per-tile variant randomisation; flood fill + line tool; reachability lint;
play-test runtime. Not in v5.
